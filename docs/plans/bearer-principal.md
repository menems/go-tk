# bearer-principal
> a service resolves the bearer of a covered request through a resolver of its own, and its handlers read the caller in the request context

**Created**: 2026-09-21
**Out of scope**: verifying the credential itself, its signature, its claims and its expiry, which stay in the resolver the service hands in; which right a principal holds, per route or otherwise, which the next plan owns; issuing, storing or reparsing a token; any scheme other than bearer, Basic, an API key and a client certificate included; optional coverage, where a route resolves a caller when one is present and serves anonymously when none is; caching what a resolver returned, and logging what it answered.
**Approach**: A bearer middleware in `transport/http` (package `httpd`, root module, stdlib only) over `authctx`: the service hands its own context key and its own resolver from token to principal, wraps the handlers of the routes it covers, and a covered request whose bearer does not resolve is refused 401 through the failure envelope the package already writes, before that handler runs; the wrap sitting on the handler, the route table still answers 404 and 405 first, so no resolver is asked about a request nobody routed. Not a gate in front of `NewRouter`, which would name the covered paths a second time in a second syntax and would resolve a bearer for a request no route matched; and not an extension of `authctx`, which would make a deliberately transport-agnostic credential vocabulary import a transport and pick a status code, closing it to the `connect.Request` caller its own doc comment names.
**Threat surface**: input: the `Authorization` header of every covered request, its scheme and its token read before any resolver sees it, nothing of a refused request being parsed further, echoed back or written anywhere. authn/authz: this is a service's authentication boundary, it establishes who the caller is and grants no right, the verdict itself belonging to the resolver handed in, so a resolver that answers wrongly authenticates wrongly; coverage is exactly the set of handlers the service wrapped, an unwrapped route being served with no principal in its context and a handler reading none having to treat that as unauthenticated; a route named for GET is reached by HEAD too, and the wrap sitting on the handler, that HEAD is resolved like the GET; the route table still answers 404 and 405 before any credential is read, so enumerating paths and methods stays anonymous exactly as `route-gate` left it, which this plan neither widens nor closes. secrets: the bearer token is a credential, it reaches no response body, no header and no error this brick builds, the resolver's own error text stays out of the answer, and the principal is carried in the context rather than written anywhere. No egress, the resolver's own calls being the service's. No dependency added, the root module keeping its stdlib-only set.
**Landmarks**: transport/http/: package `httpd`, root module, stdlib only, where this lands, beside the `NewRouter` route table a covered route is named in and the `WriteError` / `ErrorCode` failure envelope a refusal goes out through; authctx/: the credential vocabulary this builds on, `Bearer` off an `http.Header` and a `Key[T]` carrying what authentication produced, verifying nothing and naming no transport; health/: the repo's other handler, served through no table and covered by nothing, out of scope; go.mod: the root module, nothing required outside the stdlib; Makefile: `make check` is fmt-check, vet and race over every module; README.md: one H2 per package, its shape and the reason behind it, the `authctx` one carrying today the hand-rolled version of this brick as example code.

## Steps
1. [transport] Resolve the bearer of a covered route and hand the caller to its handler
   - seam: the handler `NewRouter` returns, covered and uncovered routes alike, called over a served request from the package's external test
   - acceptance: a request on a covered route carrying a bearer its resolver accepts reaches that route's handler, which reads back from the request context the principal that resolver produced; the same request carrying no `Authorization` header is answered 401 in the package's failure envelope, under a machine-readable code of its own and with a `WWW-Authenticate` header naming the bearer scheme, and that handler does not run; a route of the same table the service did not cover serves that same credential-less request through its own handler, which finds no principal in its context; a request on a path nobody named is still answered 404 and the resolver is asked nothing

2. [transport] Tell a resolver's refusal from a resolver's failure
   - seam: the same handler `NewRouter` returns, called over a served request from the package's external test
   - acceptance: a request on a covered route whose bearer its resolver refuses is answered 401 in the same envelope, with the same `WWW-Authenticate` header as a request that carried no credential, and the route's handler does not run; a request whose resolver returns a failure of its own instead of a verdict is answered 500 in that envelope under a code of its own, carries no `WWW-Authenticate` header, and that handler does not run either; a client tells the two apart from the status and the code alone, neither answer carrying the token, the resolver's error text or anything else of what arrived
