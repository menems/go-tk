# password-hash
> a service hashes and verifies a password behind one interface, the plaintext never leaving the type that carries it, on an implementation chosen at wiring

**Created**: 2026-09-22
**Out of scope**: a bcrypt or an argon2id hasher, with the module and the third-party dependency either would add, a service wanting one writing that adapter at its own wiring against the interface this package names; where a cost comes from, a service reading it from its own environment at boot, which `env-values` owns and this package names no variable for; bounding how many hashes run at once, which `work-slots` owns, so a service serving every login concurrently spends its CPU on hashes until that plan lands; re-hashing a stored value whose cost is outdated, and any upgrade path across costs beyond verifying a value made under another one; a password policy, so a minimum length, a composition rule, a breach list or a dictionary, each a fact about a service's own users; a pepper, an HSM and any key material beside the stored value itself; erasing the plaintext from memory, which a Go string does not allow; how long a verification takes seen from outside, and whether a service's answer lets an attacker learn that an account exists, which its handler owns; a token, a session or a reset flow, which `opaque-token` and the service own; logging, as in the six merged plans.
**Approach**: One package `password` under a new `crypto/` directory, in the root module, on the stdlib alone: a carrier type holding a plaintext nothing outside it reads, one interface naming both the hashing and the verification, and one implementation of that interface shipped in the box, the service naming at wiring which implementation it runs on. The directory is a group and not a package, as `storage/`, `telemetry/` and `transport/` are, none of which carries Go source at its own level, so `work-slots` and `opaque-token` land beside this brick as `storage/mysql` is promised to land beside `storage/postgres`; a package sitting at `crypto/` itself would both merge three bricks into one and shadow the stdlib's own `crypto` in a consumer using both, which is the reason `transport/http` is `package httpd`. The module is the root one because this brick needs nothing outside the stdlib: `crypto/pbkdf2` has been there since Go 1.24 and this repo builds on 1.27, so `CLAUDE.md`'s rule sending a brick that needs a third-party dependency into a module of its own does not fire, and `call-rate`'s trade is taken again, an implementation shipped behind a seam rather than a dependency chosen here on every consumer's behalf. A module of its own carrying `golang.org/x/crypto` was the alternative: it costs a consumer a second `go get` and a second tag to wait for before a merged plan is importable, and it costs this plan a wiring step for a `go.work` line, a `MODULES` entry and two documented tables, where `scripts/tag.sh` alone would need nothing, reading its modules from the tracked `go.mod` files. A root module shipping only the interface while a second module ships the implementation costs more than either, being the first module here to require another and ending the property the README measures and advertises, that taking one module never pulls a second. What the root module costs instead is named: the hasher in the box derives its key by iteration alone, the memory-cheap one of the three storage schemes anyone recommends, so a service whose stolen table would be worth cracking on GPUs writes a bcrypt or an argon2id adapter at its own wiring, in its own module, where that dependency belongs, exactly as this repo already asks every service to write its own five-line adapter; and the stored value carries the parameters it was made under, so a service raising its cost still verifies everything it stored before. Containment is a property of the type rather than a convention anyone must remember: the plaintext sits behind one indirection, so a struct holding the carrier in an unexported field cannot have it reflected out by a formatter, and every surface a value leaks through is closed by the hook Go gives for it, `String` for the verbs `fmt` routes through it, `GoString` for `%#v`, `MarshalJSON` and `MarshalText` for an encoder, `LogValue` for a handler. Marshalling redacts instead of failing, because a service that puts a password in an outgoing payload has a bug and a toolkit answering it with an error decides an outage on that service's behalf; what it costs is that the bug ships a redacted member rather than stopping at the boundary. Unmarshalling is the asymmetry that makes the rest worth anything: a login body decodes into the carrier directly, so the plaintext is inside it from the moment it enters, instead of passing through a plain string field in a struct someone prints.
**Threat surface**: input: the plaintext, entering through the type's own unmarshalling from a request body whose size `json-envelope`'s decoder bounds and this package bounds no further, an empty one refused at construction and the zero value of the carrier holding no secret, so nothing derived from it ever verifies; and the stored value, entering verification from the service's own store, parsed before it is trusted, one this package did not write, one truncated, one carrying parameters it cannot read and an empty one each refused under an error rather than matching anything. authn/authz: this identifies nobody and grants nothing, answering one question about one stored value and one candidate; it knows no account, no user and no session, so whether a service's answer lets an attacker learn that an account exists, and whether two verifications take comparably long seen from outside, stay that service's handler's; a verification that failed and a verification that could not run are distinct errors, so a caller fails open only by ignoring what it was told. secrets: the plaintext is the secret this package exists to hold, and it leaves the carrier through nothing, no accessor returning it, no verb of `fmt` printing it, `%#v` included through the `GoString` hook `fmt` documents for it, no encoder marshalling it and no `slog` handler receiving it, a struct holding it in an unexported field printing no more than one holding it in an exported one; a stored value and a candidate are compared in constant time, so a mismatch tells an attacker nothing about how far it got, and so are two plaintexts compared against each other, the carrier offering that comparison so a caller can check a password against its own confirmation without either leaving its type, with the bound that a constant-time comparison returns at once when the two lengths differ, so a plaintext's length is observable in timing where its bytes are not, which is inherent to comparing two secrets of unequal length and is left visible rather than hidden; a refused verification's error repeats no part of the password and no part of the stored value, and is the same error whatever the password was; this package writes no log line and no file, and it does not promise the plaintext is erased from memory, a Go string being immutable and copied by its collector, which is the bound a service holding one for longer than a request should know. egress: none, a password is derived and compared and nobody is contacted. dependencies: none added, the root module keeping its stdlib-only set.
**Landmarks**: crypto/password/: new, package `password`, root module, stdlib only, where this lands, the first brick under a `crypto/` that `work-slots` and `opaque-token` will share; authctx/: the repo's other credential brick, reading a bearer and carrying a principal while verifying nothing, untouched here; transport/http/: package `httpd`, root module, where a brick built at wiring refuses a bad argument there rather than later; config/: how a service reads its environment at boot, this package naming no variable of its own; go.mod: the root module, nothing required outside the stdlib, which this brick keeps; README.md: one H2 per package, its shape and the reason behind it, plus the `Layout` block and the `Dependencies` table, two consumer-facing lists a new package has to stay true in.

## Steps
1. [crypto] Hold a password in a type nothing reads it out of
   - seam: the package's exported carrier type and the whole formatting, encoding and logging surface it offers, from the package's external test
   - acceptance: a carrier built from a plaintext, formatted with `%v`, `%s`, `%q`, `%+v` and `%#v`, printed through its own string method, marshalled by the JSON encoder, marshalled as text, and logged as an attribute through both the JSON and the text handler of `log/slog`, gives the same fixed redaction every time and an output carrying no part of that plaintext; the same holds under `%v`, `%+v` and `%#v` for a struct holding the carrier in an exported field and for one holding it in an unexported field; the package's exported surface hands the plaintext to no caller, no exported field, method or function returning it, which is checkable by reading; a carrier decoded from a JSON string and one decoded from text each hold the plaintext they were given, an empty plaintext is refused under an error at construction and at either decoding, and the zero value of the carrier holds none and redacts like any other

2. [crypto] Hash and verify behind one interface, on the hasher wired in
   - seam: the package's exported hashing interface, built at wiring with a hasher the test writes and with the hasher this package ships, from the package's external test
   - acceptance: a hasher the test writes and hands in at wiring is the one every hash and every verification goes through, this package choosing none on its own; with the hasher this package ships, a stored value made from a password verifies against that same password and is refused against any other; hashing one password twice gives two different stored values, each verifying that password; a stored value this package did not write, one truncated, one whose parameters it cannot read and an empty one are each refused under an error and match nothing; a stored value made under one cost verifies through a hasher built with another, and a hasher built with no cost named uses the one this package names; a hasher built with a cost below one is refused at wiring under an error naming the value, and nothing is hashed; a refused verification's error is the same whatever the password, and carries no part of the password and no part of the stored value; the zero value of the carrier is refused rather than hashed
